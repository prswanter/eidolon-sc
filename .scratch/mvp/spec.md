# Eidolon-SC MVP

Status: ready-for-agent

术语以 `CONTEXT.md` 为准；相关决策见 ADR-0001（日语回复加中文字幕）、ADR-0002（共享记忆并标注来源角色）、ADR-0003（剧情库与音色仅限私用）。

## Problem Statement

我想和《偶像大师 闪耀色彩》里的偶像「真的」说上话：打一通语音电话，听到她们用本人的声线、熟悉的口癖和语气回应我；她们记得和我（制作人）一起走过的原作剧情，也记得我们之前聊过什么。

LAPLACE Eidolon 已经为虚拟主播明前奶绿做出了这样的实时语音 AI 分身，但它有三个问题：

- 源码没有公开；
- 整套数据模型都围绕一位主播搭建：直播录播、B 站 UID、本人授权的声线；
- 只有一个角色。

游戏角色的情况完全不同：

- 没有直播，只有原作剧情；
- 同一个作品里有多位角色；
- 用户和角色之间有原作设定好的关系：用户就是她们的制作人。

我还想把它分享给小圈子里的朋友，每个人和角色之间都有各自的记忆，但不能因此耗光我的 API 额度。

## Solution

一个供自己和小圈子使用的 Web 应用。用户选择一位角色（MVP 为櫻木真乃、月岡恋鐘）后开始一次对话：

- 用户可以直接说话，也可以打字，中文、日文都可以。
- 角色以本人的日语声线实时回复，界面同时显示日语原文和中文字幕。
- 角色把用户当作 283 事务所的制作人，能回忆自己出场过的原作剧情（仅限正式经历），也会主动用「回顾剧情」工具回答「那次……是怎么回事」这类问题。
- 关于用户的记忆，由所有角色共享：对真乃说过的事，恋鐘也会以转述的口吻知道。
- 每位用户持有自己的访问密钥，在任意设备上填入同一把密钥，就能延续同一份记忆。
- 用户可以设置称呼、性别和时区，也可以查看和删除角色关于自己的记忆。

## User Stories

### 访问与身份

1. 作为管理员（我自己），我想为小圈子里的每位朋友签发访问密钥，以便他们能使用系统而陌生人不能。
2. 作为管理员，我想让一位用户持有多把访问密钥，以便同一个人在不同设备或场景下使用不同的密钥，但仍是同一位用户。
3. 作为管理员，我想吊销某一把访问密钥，以便在密钥泄露时止损，而不影响该用户的记忆和档案。
4. 作为用户，我想在设置页填入访问密钥后才能开始对话，以便我的记忆不会被别人看到或改写。
5. 作为用户，我想在电脑和手机上填入同一把访问密钥，以便在两台设备上看到的是同一份记忆和档案。
6. 作为用户，没有填入有效密钥时，我想看到明确的提示，而不是一个莫名其妙的错误。
7. 作为管理员，我想让限流和用量统计按用户计算，以便某位朋友用得多时不会耗光所有人的 API 额度。
8. 作为用户，当我达到限额时，我想看到友好的提示，并知道什么时候可以再用。
9. 作为管理员，我希望以后接入第三方登录时，只需要新增「登录方式 → 用户」的对应关系，不需要迁移任何记忆。

### 制作人档案

10. 作为用户，我想被角色当作 283 事务所的制作人对待，以便对话和原作里的关系保持一致。
11. 作为用户，我想设置一个自定义称呼，以便角色在合适的场合用这个名字叫我，而我仍然是她们的制作人。
12. 作为用户，没有设置称呼时，我希望角色按各自的习惯叫我（例如真乃叫「プロデューサーさん」）。
13. 作为用户，我想设置自己的性别，以便角色当下对待我的方式和我相符。
14. 作为用户，没有设置性别时，我希望角色沿用原作中制作人的设定。
15. 作为用户，我希望修改性别不会改写角色回忆中的原作剧情内容。
16. 作为用户，我希望系统默认使用我当前浏览器检测到的时区，以便角色口中的「今天」「今晚」和我的感受一致。
17. 作为用户，我想手动指定时区，覆盖自动检测的结果。
18. 作为用户，我希望角色知道现实中的当前日期和时间，例如在她生日那天或节日时自然地提起。

### 角色选择

19. 作为用户，我想在角色选择页看到可以对话的角色，每位都有头像和简介，以便选择今天和谁聊。
20. 作为用户，我想点击某位角色后进入和她的对话页。
21. 作为管理员，我想通过配置新增角色（人设、角色资料、音色 ID），而不用改代码。
22. 作为管理员，我想通过配置替换某位角色的音色 ID，以便公共音色下架后可以换成自己的私有音色。

### 对话：语音与文字

23. 作为用户，我想和一位角色进行实时语音通话，以便像打电话一样和她聊天。
24. 作为用户，我想在通话中随时打字输入，文字和语音记录在同一条对话里，以便在不方便说话时也能继续聊。
25. 作为用户，我想用中文或日文说话、打字，以便按自己舒服的方式表达。
26. 作为用户，我想听到角色用本人的日语声线回复，以便感觉就是在和她本人说话。
27. 作为用户，我想看到角色每句回复的日语原文和中文字幕，以便听不懂日语时也能跟上。
28. 作为用户，我想打开静音开关，只看文字回复不播放语音，以便在安静的场合使用。
29. 作为用户，我想看到这次对话的记录（我说的话，以及角色的日语原文和中文字幕），以便回看刚才聊了什么。
30. 作为用户，我希望角色的回复延迟尽量低，以便对话像实时聊天而不是收发邮件。
31. 作为用户，我想在设置页选择麦克风和通话音质。
32. 作为用户，我希望角色始终保持自己的人设（自称、口癖、对他人的称呼），不会说出明显不符合角色的话。
33. 作为用户，我希望每次对话只有一位角色，不会被其他角色插话。

### 剧情回忆

34. 作为用户，我希望角色能在聊天中自然地提起我们一起经历过的原作剧情，以便感觉她真的记得。
35. 作为用户，我想问「那次拍写真集是怎么回事」这类概括性问题，由角色通过「回顾剧情」工具查到对应剧情后回答我。
36. 作为用户，我希望角色只回忆她自己出场过的剧情，不会把别的偶像身上发生的事说成是自己经历的。
37. 作为用户，我希望角色只把成功路线当作真实经历，不会同时「记得」自己在 W.I.N.G. 里夺冠又落败。
38. 作为用户，我希望遇到剧情里的选项分支时，角色不会断言我当时选了哪一项。
39. 作为用户，我希望角色只在需要时才去查剧情库，以免闲聊时回复变慢。

### 记忆

40. 作为用户，我希望角色记住我在对话中透露的信息（比如我感冒了、我喜欢什么），并在之后的对话中用上。
41. 作为用户，我希望新开一次对话时，角色能通过检索记忆接上以前聊过的事。
42. 作为用户，我希望对真乃说过的事，恋鐘也会知道，并且她会以转述的口吻说出来（例如「听真乃说……」），而不是说成我亲口告诉她的。
43. 作为用户，我希望自己的记忆和其他用户的记忆完全隔离。
44. 作为用户，我想在记忆管理页看到角色关于我的所有记忆，每条都注明来源角色，以便知道她们记住了什么。
45. 作为用户，我想逐条删除记错或不想保留的记忆。
46. 作为用户，我想一键清空关于我的全部记忆，以便重新开始。
47. 作为用户，我希望记忆用中文记录，以便我自己能看懂。

### 角色资料与剧情库的构建

48. 作为管理员，我想用一个导入命令把 SCTranslationData 格式的剧情 CSV 导入剧情库，以便角色可以回忆这些剧情。
49. 作为管理员，我想导入游戏原始剧本 JSON，以补全 SCTranslationData 中缺少的剧情。
50. 作为管理员，我希望导入时自动识别每段剧情的出场角色，以便用来限制每个角色能回忆哪些剧情。
51. 作为管理员，我希望导入时自动排除失败结局，只保留正式经历。
52. 作为管理员，我希望导入时生成按「角色 → 卡或活动 → 话」分层的剧情目录。
53. 作为管理员，我希望重复导入同一段剧情不会产生重复数据，以便原作更新后可以随时重新导入。
54. 作为管理员，我想用后台模型从剧情库中为角色生成人设初稿，再手工校对，以便不用从零开始写人设。
55. 作为管理员，我想维护每位角色的角色资料（档案和人物关系），供对话时检索。
56. 作为管理员，我希望整理后的剧情库数据不会被提交到仓库，只提交导入脚本和配置结构。

### 模型与服务配置

57. 作为管理员，我想分别配置「对话模型」和「后台模型」，每一项都能选 OpenAI 兼容接口、OpenAI Responses 接口或 Anthropic 接口，并自填地址、密钥和模型名。
58. 作为管理员，如果配置的对话模型不支持流式输出或工具调用，我希望启动时就收到明确的报错。
59. 作为管理员，我想配置 Soniox、Fish Audio、硅基流动（向量化与重排）、Vercel AI Gateway（Jev）的密钥。
60. 作为管理员，我想用一条命令把整套服务部署到 VPS 上。

## Implementation Decisions

### 整体结构

- 后端用 Python，基于 Pipecat；前端用 Next.js 和 Pipecat 客户端，通过 WebRTC 连接。部署在 VPS 上，用 Docker Compose 编排。
- 后端的核心是一个**不依赖语音的「对话引擎」**深模块。它接收一次对话回合（用户、角色、对话、输入文本），返回角色的回复（日语原文和中文字幕），并在内部完成以下工作：拼装人设、判断是否需要检索、检索剧情和记忆、调用「回顾剧情」工具、写入记忆。
- Pipecat 管线只是外面薄薄的一层：Soniox 语音识别 → 对话引擎 → 只把日语部分交给 Fish Audio 合成语音；中文字幕则通过数据通道推给前端。文字输入直接进入同一个对话引擎，写入同一条对话记录。
- 「回顾剧情」工具调用和记忆写入都在对话引擎内部完成，**不使用** Pipecat 自带的 LLM 服务和上下文聚合器，这样整条对话逻辑都能脱离语音来测试。

### 对话引擎内部的主要模块（每个都通过接口注入，便于替换）

- **LLM 提供方**：统一的「流式对话，支持工具调用」接口，有三种实现：OpenAI 兼容 Chat Completions、OpenAI Responses、Anthropic Messages。配置时分「对话模型」和「后台模型」两个槽位。启动时检查对话模型是否满足流式输出和工具调用的要求。
- **回复格式**：对话模型一次输出结构化结果（日语原文和中文字幕），并以流式方式解析，让 TTS 能尽早开始读日语部分。如果实测格式不稳定，再退回「只输出日语，然后单独翻译」（ADR-0001）。
- **检索判断**：用 Jev（通过 Vercel AI Gateway 调用）判断当前这句话是否需要检索，避免闲聊时白白增加延迟。
- **检索**：用硅基流动上的 Qwen3-Embedding 做向量化，Qwen3-Reranker 做重排。检索的对象有三类：剧情库、角色资料、记忆。
- **剧情检索**必须用出场角色过滤，只返回当前角色出场过的剧情。
- **「回顾剧情」工具**：基于剧情目录，接收一个概括性的查询，返回相关剧情的摘要或片段。
- **记忆**：在对话进行中或结束后，由后台模型抽取中文记忆事实，每条带上用户和来源角色。检索时只取当前用户的记忆，然后在提示词里标明每条记忆的来源角色，要求来源不是当前角色的记忆用转述的口吻说出。不带上次对话的摘要。
- **提示词拼装**：人设（完整）+ 制作人档案（称呼、性别）+ 按用户时区计算的当前日期时间 + 检索结果 + 本次对话历史。

### 身份与访问

- 数据模型：「用户」有一个稳定的内部标识；「访问密钥」多对一关联到用户，可以吊销。记忆、制作人档案、对话记录都以用户标识为外键。
- 每个请求（包括建立 WebRTC 连接）都要带访问密钥，在服务端解析出对应的用户。管理员通过命令行签发和吊销密钥。
- 限流按用户计算。

### 数据存储

- 用一个嵌入式关系库保存用户、访问密钥、制作人档案、对话记录（日语原文和中文字幕两份）、记忆条目和剧情目录。
- 用一个嵌入式向量库保存剧情、角色资料和记忆的向量。
- 整理好的剧情库和人设文件不进仓库（ADR-0003）。

### 剧情库导入（离线的批处理流程）

- 输入两种格式：
  - SCTranslationData 格式的 CSV（`id,name,text,trans`，结尾有一行 `info` 指向原始剧本）；
  - 游戏原始剧本 JSON（字段包括 speaker、text、select、voice 等）。
- 输出：
  - 剧情：分类、出处（卡或活动）、标题、出场角色、按说话人分好的台词；
  - 剧情目录：按「角色 → 卡或活动 → 话」分层；
  - 向量索引。
- 规则：
  - 只收录正式经历，排除失败结局。选项分支只保留角色的反应，不保留制作人选了哪一项。
  - 出场角色根据台词的说话人识别，并映射到规范的角色标识；制作人和非角色人物不算出场角色。
  - 以剧情的来源标识为主键，重复导入时覆盖更新，不会重复插入。
- 人设初稿的生成是另一条独立命令：调用后台模型，基于某位角色出场的剧情生成人设草稿，交给人工校对。

### 接口（后端对外）

- 建立语音连接：WebRTC 信令、ICE 服务器配置（对应参考项目中的 `offer` 和 `ice-servers`），需要带访问密钥和角色标识。
- 文字对话回合：输入角色、对话和一句话，流式返回日语原文和中文字幕。
- 角色列表：头像、简介（不返回人设内容）。
- 制作人档案：读取和更新。
- 记忆：列出（带来源角色）、删除单条、一键清空。

### 配置

- 每位角色的配置：规范标识、显示名、头像、简介、Fish Audio 音色 ID，以及人设和角色资料的位置。
- MVP 的角色：櫻木真乃（音色 `a1150f3d14ac46fb8ea59c7803cd8357`）、月岡恋鐘（音色 `a11bfd046e924099a84f989fb4049e95`）。这两个都是公共的粉丝模型，没有授权，随时可能下架，所以必须能通过配置替换。
- 所有外部服务的密钥和地址都通过环境变量配置。

### 前端

- 四个页面：
  - **角色选择**；
  - **对话**：语音按钮、文字输入框、日语原文加中文字幕的记录、静音开关；
  - **设置**：访问密钥、制作人档案（称呼、性别、时区）、麦克风、音质；
  - **记忆管理**。
- 时区默认用浏览器检测到的值，检测不到时用 Asia/Shanghai；用户手动设置后以手动设置为准。

## Testing Decisions

- **好的测试只验证外部行为**：给定输入（请求、剧情文件），断言可以观察到的输出（回复内容和结构、接口返回、剧情库和目录的查询结果），不断言内部调用顺序或私有结构。
- **切入点 A：后端对外接口**（主要切入点）。通过后端对外接口驱动文字对话回合和管理类接口；LLM、向量化、重排、Jev、Soniox、Fish Audio 全部换成测试用的假实现。假 LLM 能记录它收到的提示词和工具定义，也能按剧本返回工具调用和结构化回复。重点覆盖以下规则：
  - 没有访问密钥或密钥无效时拒绝请求；多把密钥解析到同一位用户；吊销的密钥失效；
  - 不同用户的记忆互相隔离；
  - 一个角色检索不到自己没有出场的剧情；
  - 来源角色会带进提示词，并影响转述的措辞要求；
  - 称呼、性别、时区会进入提示词，当前时间按用户时区计算；
  - 回复同时包含日语原文和中文字幕，并且两者都写进对话记录；
  - 「回顾剧情」工具调用后返回的是剧情目录里的内容；
  - 记忆可以列出、逐条删除、一键清空；
  - 超过限额时被拒绝；
  - 对话模型不满足流式输出和工具调用要求时，启动失败。
- **三种 LLM 协议的适配器**，用各自协议的录制响应做契约测试：确认流式解析和工具调用解析正确。
- **切入点 B：剧情库导入**。准备少量样例剧情文件（CSV 和 JSON，包含成功和失败结局、选项分支、多位出场角色、非角色的说话人），导入后通过剧情库和剧情目录的查询来断言：
  - 失败结局被排除，选项分支处理正确；
  - 出场角色识别正确；
  - 目录层级正确；
  - 重复导入是幂等的。
- **语音链路和前端**不做自动化测试，通过手动打电话和冒烟测试验收：延迟可以接受、字幕和语音对得上、静音生效。
- 已有测试：没有，这是一个新仓库。后端使用 pytest。

## Out of Scope

- 自拍工具（保留为扩展点，MVP 之后再做）
- 多人群聊
- 第三方账号登录（只保留从登录方式映射到用户的扩展点）
- 除真乃和恋鐘之外的其余角色（通过配置扩展）
- 切换声线的工具
- 公开的 MCP 接口或剧情查询接口
- 用户自建角色
- 联动角色，以及可对话的非偶像人物
- 手动新增或修改记忆
